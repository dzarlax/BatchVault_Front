Валюта организации в профиле

26 сентября 2026 · Реализовано и выпущено: backend, web, TestFlight 1.0 (60) · Смена валюты в production включена и проверена

1. Согласованное поведение

У организации одна валюта для всех участников. Пользователь переключает её в профиле. Числа не пересчитываются: при смене RSD → EUR сумма 100 RSD становится 100 EUR. Это относится и к уже существующим заказам, ценам, себестоимости и аналитике.

Предлагаемый объём: серверное хранение и API в BatchVault_Back, интерфейс настройки и все денежные экраны в BatchVault_Front. Курсы, конвертация, отдельная валюта каждой операции и личные валютные предпочтения не требуются.

2. Что подтверждено кодом

  • Текущая граница общих данных — Workspace. На сервере есть membership и роли owner/manager/operator/viewer, запросы используют X-Workspace-ID. Отдельную модель организации для этой задачи не добавляем.
  • models/workspace.go и WorkspaceResponse не содержат валюту. Есть GET /api/workspaces и GET /api/workspaces/current, маршрута изменения настройки пока нет. Модели мигрируются через GORM AutoMigrate.
  • Во всех трёх переводах currency равен RSD. Его используют dashboard, рецепты, ингредиенты, цены, заказы, карточки товаров и модальные формы.
  • profile.tsx содержит данные аккаунта и смену пароля. workspaceContext.tsx уже хранит выбранный workspace и умеет перечитывать список, но не обновляет его периодически.
  • fetcher.ts сейчас завершает сессию при любом 403. Для отказа в смене валюты потребуется точечная обработка без logout.
  • В iOS и виджете валюта тоже жёстко задана как RSD: Extensions.swift, вызовы formattedRSD, BatchVaultWidget.swift. Дополнительное поле API само по себе это не исправит.

Frontend main совпадает с origin/main после fetch. В обоих репозиториях есть посторонние локальные изменения. Backend изучен в текущем локальном checkout; перед реализацией нужно сверить его с актуальным origin/main и сохранить имеющуюся работу.

Распределение работы: Терра и Луна

Терра — ведущая модель и владелец результата. После согласования сверяет актуальные состояния обоих репозиториев, фиксирует точный серверный контракт и правила каталога, права owner и поведение миграции. Реализует или непосредственно принимает изменения серверной модели и PATCH, где ошибка может изменить данные или доступ. Проверяет код Луны по реальному diff, интегрирует части, выполняет общие тесты и ручную проверку реального сценария. Отвечает за итоговый отчёт и запись фактических результатов в этот план.

Луна — исполнитель больших ограниченных частей. После решения Терры о критериях ISO 4217 готовит воспроизводимое обновление локального справочника SIX и проверки его состава. После фиксации ответа GET/PATCH и прав выполняет связанный фронтенд-пакет: типы, контекст workspace, поиск валют в профиле, переводы и замену RSD на валюту workspace во всех денежных экранах и формах. Проверяет свой пакет lint, typecheck, build и доступными UI-проверками; передаёт Терре перечень изменённых файлов и результаты. Никаких самостоятельных решений о миграции, правах или смысле старых сумм.

Зависимости и приёмка. Сначала Терра уточняет контракт GET /api/currencies, поле currency, PATCH, статус 403 и критерии активных денежных кодов. Затем Луна может брать каталог и фронтенд как отдельные пакеты, не изменяя одновременно одни и те же файлы. На первом контрольном рубеже Терра принимает каталог и серверный контракт; на втором — проверяет фронтенд на всех денежных путях, смене workspace и ошибках API. Несоответствие исправляется до общей проверки, а не считается завершённой работой.

Это рекомендуемые роли исполнения после одобрения плана. Они не означают, что модели уже запущены, и сами по себе не дают права на коммит, push, PR или deployment. Sol/Astra привлекаются только при конкретной сложной неоднозначности; обязательного рецензирования ими нет.

3. Предлагаемый контракт и интерфейс

  • Добавить workspaces.currency, обязательное поле с default RSD. Существующим workspace заполнить RSD; повторный запуск миграции не меняет выбранную валюту и денежные значения.
  • Отдавать currency в обоих workspace GET. Добавить PATCH /api/workspaces/current с телом {"currency":"EUR"} и ответом обновлённого WorkspaceResponse.
  • Поддерживать все действующие денежные валюты ISO 4217 из официального справочника SIX List One: Current Currency & Funds. Включать записи денежных валют; исключать специальные коды фондов, металлов, расчётных единиц и «нет валюты». Исторический List Three не предлагается для новых настроек.
  • На сервере хранить версионированный локальный снимок допустимых кодов с датой источника и воспроизводимым способом обновления. Не обращаться к SIX на каждом запросе и не принимать любой трёхбуквенный код. Изменения справочника вносятся контролируемым обновлением и проверяются тестами.
  • Серверный GET /api/currencies отдаёт тот же каталог, которым PATCH проверяет выбор. В профиле — поиск по коду и названию; текущая валюта видна первой. Локализованные названия можно получать через браузерный Intl с кодом как запасной подписью, но допустимость определяет сервер.
  • Если сохранённая валюта позже станет исторической, продолжать показывать её код и правильно отображать старые суммы; запретить только новый выбор снятого с обращения кода. Язык интерфейса не определяет валюту.
  • Предлагаемое право изменения — только owner. Все участники видят значение. Сервер проверяет роль и membership; скрытая кнопка не заменяет проверку прав.
  • В профиле — карточка «Валюта организации», имя текущей организации, SelectDropdown и кнопка сохранения. Перед сменой явно подтвердить отсутствие пересчёта и применение к старым данным. Не показывать успех до ответа API.
  • После сохранения обновить workspace в общем контексте. Другие открытые клиенты перечитывают настройку при возврате фокуса и периодически, предлагаемый интервал — 60 секунд. Мгновенная доставка через WebSocket не требуется.
  • Запрос сохранения фиксирует workspace ID на момент отправки; переключение организации во время запроса не должно применить ответ к другой организации. Ошибка фонового обновления сохраняет последнее подтверждённое значение.
  • Единый hook/helper получает валюту из выбранного workspace. Все денежные подписи, поля и tooltips используют его; точность существующих чисел сохраняется. Во время первой загрузки не показывать произвольную RSD вместо неизвестной валюты.
  • Отсутствующее поле у старого API допускает RSD для чтения; неизвестный непустой код не подменяется молча. Несуществующий PATCH показывает ошибку, локальное «сохранение» не имитируется.

6. Риски, совместимость и откат

Главный продуктовый эффект согласован: валюта старых сумм меняется без конвертации. Подтверждение в интерфейсе должно объяснять это до сохранения.

iOS/виджет пока показывают RSD независимо от серверной настройки. Поэтому готовность web + backend не означает готовность всего продукта. Перед включением другой валюты в production требуется согласовать и выполнить обновление мобильного клиента/виджета и порядок перехода со старых версий. Их реализация не включена в данный web/backend-план автоматически.

Рекомендуемый порядок выпуска после отдельного разрешения: аддитивный backend, совместимые клиенты, затем использование новых валют. Не включать смену валюты до готовности нужных клиентов.

Откат до использования других валют: вернуть предыдущие приложения, поле БД оставить. После выбора других валют нельзя откатывать UI к жёсткой RSD: сначала отключить редактирование, сохранив чтение/отображение валюты. Массово сбрасывать currency или удалять колонку нельзя.

8. Фактический результат после реализации

Распределение работы. Луна подготовила версионированный снимок каталога SIX и пакет изменений фронтенда; Терра реализовала серверное хранение, API и тесты прав/миграции. Ведущий агент проверил diff, интеграцию, тесты и локальный пользовательский путь. Части выполнялись в отдельных рабочих деревьях, посторонние изменения исходных checkout не затронуты.

Backend. В Workspace добавлено обязательное currency с default RSD; оба GET workspace возвращают поле. Защищённый JWT GET /api/currencies отдаёт локальный каталог, owner-only PATCH /api/workspaces/current принимает ровно одно поле currency, проверяет код по тому же каталогу и активное членство owner при обновлении. Проверки охватывают ответы API, запрещённые коды/роли, чужую организацию и повторную миграцию SQLite. Снимок официального SIX List One датирован 17 сентября 2026: 155 активных денежных кодов; генератор и инструкция обновления входят в пакет.

Frontend. Профиль показывает валюту текущей организации всем участникам; owner может найти валюту по коду или названию и сохранить её после явного предупреждения об отсутствии конвертации. Контекст организации хранит подтверждённую валюту, обновляет её при фокусе и каждые 60 секунд, защищает от ответа для прежнего аккаунта/организации. Денежные подписи на dashboard, страницах, карточках, формах и графиках используют валюту выбранной организации. Для старого API предусмотрен RSD при отсутствии поля; сохранённый код вне актуального каталога остаётся виден, но не предлагается для нового выбора. Добавлены EN/RU/RS переводы. Для 403 от PATCH показана ошибка без выхода из аккаунта; 401 сохраняет прежнюю обработку.

Проверено. go test ./models ./database ./controllers ./routes ./currencycatalog, npm run lint, npx tsc --noEmit, npm run build:docker и git diff --check прошли. Через браузер с локальным тестовым API: вход владельца, выбор RSD → EUR и подтверждение, обновление профиля и подписей dashboard без изменения чисел; переключение на вторую организацию показало её USD. 9. Новая цель: доведение до production — состояние на 26 сентября

Пользователь поручил довести функцию до production, одобрил этот этап и уточнил, что используемое iOS-приложение собрано из локального незакоммиченного состояния, а не из GitHub. Все содержательные прежние локальные изменения в iOS, frontend и backend должны быть сверены и доведены до релиза. Исходные dirty checkout сохраняются без перезаписи; сборочные файлы, настройки редактора и секреты не включаются в релизные коммиты.

  • После свежего git fetch origin main фронтенд, backend и iOS не отстали от своих origin/main. Изменения валюты в web/backend остаются незакоммиченными в изолированных ветках.
  • iOS стоит на e0a2c47 и имеет большой незакоммиченный пакет в 32 отслеживаемых файлах плюс новые исходники/планы: API, профиль, заказы, цены, локализации, APNs и виджет. Пользователь подтвердил: проверить и включить пакет. В текущем iOS-коде 55 упоминаний RSD/форматтеров в 11 Swift-файлах; Workspace не декодирует валюту, а виджет выводит RSD независимо от API.
  • Production на VPS: два контейнера JerkyVault запущены, по 0 рестартов; web https://admin.jerky.in.rs/ ответил 200, новый GET /api/currencies пока отвечает 404. Реального пользовательского пути это не подтверждает.
  • Production Compose использует ghcr.io/dzarlax/jerky-vault-back и ghcr.io/dzarlax/jerky-vault-frontend. Backend CI публикует первый образ, frontend CI — только ghcr.io/dzarlax/batchvault-front. Локальный Compose отличается от серверного и содержит чувствительные настройки; его нельзя копировать на VPS как часть этого релиза.
  • Полный backend Go suite блокируется существующей ошибкой тестовой фикстуры уведомлений: модель PushDevice.Enabled имеет default true, а тест создаёт Enabled: false через GORM Create, что записывает default true. На чистом origin/main воспроизводится тот же лишний четвёртый delivery.
  • Локальный Docker daemon и PostgreSQL CLI сейчас недоступны. Поэтому требуется отдельная изолированная PostgreSQL-проверка перед миграцией production.

Луна получает ограниченные пакеты после фиксации контракта: инвентаризацию всех денежных поверхностей iOS/виджета, замену форматирования и локализации, тестовые сценарии и frontend CI-тег. Ведущий агент проверяет итоговые diff и реальный путь, не принимая отчёт о сборке за доказательство работоспособности.

  1. Сохранить и принять локальную базу. Зафиксировать снимки dirty diff и значимых untracked исходников, сверить frontend/backend изменения валюты со старыми локальными правками, а для iOS создать отдельное рабочее дерево от свежего origin/main и перенести туда используемый локальный пакет. Проверить объединённые diff на случайные артефакты, секреты, незавершённые APNs/UI-изменения и регрессии. Исходные checkout не перезаписывать; релизные ветки включают пакет только после сборки, тестов и ручной приёмки.
  2. Закрыть iOS и виджет. Добавить обратно совместимое поле Workspace.currency с RSD только при отсутствии поля в старом API. Хранить выбранную валюту вместе с workspace в общей App Group; синхронизировать на переключении workspace, повторном открытии приложения и обновлении виджета. На всех денежных экранах, в форме заказа/цены, аналитике и виджете заменить жёсткий RSD на код выбранной организации без пересчёта и без изменения точности сумм. В iOS-профиле дать owner тот же поиск валют и подтверждение, прочим ролям — только чтение. Проверить устаревший ответ после смены аккаунта/workspace и корректную очистку общего состояния при logout.
  3. Закрыть серверный и web-барьеры. Исправить тестовую фикстуру APNs без изменения логики отправки; добиться полного go test ./.... Прогнать миграцию на изолированной PostgreSQL-схеме с существующей строкой RSD, новой строкой, повторным запуском после EUR и неизменными денежными полями. Проверить реальный web/backend путь с двумя организациями и ролями, ошибки 403/400/сети, все денежные экраны и EN/RU/RS.
  4. Сделать выпуск управляемым. Добавить серверный флаг разрешения PATCH, выключенный по умолчанию в production, чтобы обновлённый backend можно было поставить раньше iOS, не открывая смену валюты старым клиентам. GET и чтение RSD остаются совместимыми. Добавить к frontend CI тег существующего production-образа jerky-vault-frontend, сохранив нынешний batchvault-front; серверный Compose и секреты не перезаписывать. Зафиксировать SHA образов и состояние до выпуска.
  5. Выпустить последовательно. После ревью и CI — аддитивный backend с выключенным PATCH; проверить миграцию, контейнер и настоящий авторизованный путь на RSD. Затем выпустить iOS/виджет через TestFlight, подтвердить установку новой версии на используемых устройствах и реальный путь выбора/отображения. Затем поставить web-образ и включить PATCH; подтвердить RSD → EUR на заранее подготовленной изолированной production-организации, неизменность чисел и одинаковое отображение в web/iOS/виджете, после чего вернуть тестовую организацию в исходное состояние. Каждый шаг фиксирует наблюдаемый результат до следующего.

11. Приёмка, риски и откат

  • Backend: весь Go suite, PostgreSQL-миграция/повторная миграция, owner-only PATCH, неверные коды, чужой workspace, JWT, RSD default, неизменность сумм; CI публикует нужный digest.
  • Web: lint, TypeScript, production build, реальный API и браузерный прогон по всем денежным маршрутам, переключение workspace/аккаунта, исторический код и 403 без logout, EN/RU/RS и мобильная ширина.
  • iOS: сборка app + widget, тесты, Simulator с тестовыми организациями, фактические суммы на экранах/виджете, роли, logout, смена workspace, отказ API и старый API. Подписанная TestFlight-сборка должна пройти обработку и запуск на устройстве; факт загрузки в Organizer недостаточен.
  • Production: свежий backup/восстановимость БД, сохранённые конфигурация и исходные digests, контейнеры без новых рестартов/ошибок, публичные HTTP и авторизованный путь. Нельзя включать новую валюту, пока используемые iOS-клиенты не обновлены или не ограждены от неверного отображения.

Откат. До первого выбора валюты, отличной от RSD, можно вернуть прежние образы, сохранив добавленную колонку. После изменения валюты нельзя возвращать клиент с жёстким RSD: выключить PATCH и откатываться только на валютно-совместимые образы. Значения currency и денежные данные не сбрасывать.

Канал iOS подтверждён пользователем: только TestFlight. Перед включением PATCH нужно проверить, что используемые TestFlight-устройства обновились; факт загрузки сборки недостаточен. Текущий большой iOS-пакет также требует отдельного review до публикации.

12. Барьер согласования расширенного этапа

После одобрения этого дополнения можно выполнять iOS-реализацию, изолированные PostgreSQL-проверки, связанные исправления, коммиты, push, PR и подготовку релизных образов. Публикация iOS-сборки, merge и поэтапное production-обновление входят в цель «довести до прода» только после прохождения перечисленных проверок и контрольных точек. При обнаружении нового риска для данных или клиентов требуется остановиться и пересогласовать конкретное изменение. До согласования этого расширения production и текущие dirty checkout остаются без изменений.

13. Фактическое состояние расширенного этапа

Раздел 8 сохраняет исторический результат первого web/backend-этапа; его перечисленные ограничения заменены проверками ниже. Исходные грязные checkout трёх репозиториев сохранены. Релизные ветки включают содержательные локальные изменения, включая прежний iOS-пакет, не вошедший в GitHub; временные сборочные файлы, настройки редактора и бинарный backend-файл в коммиты не переносятся.

Backend. Каталог содержит 155 действующих денежных кодов SIX ISO 4217. Добавлены currency с RSD по умолчанию, owner-only PATCH и выключенный по умолчанию флаг WORKSPACE_CURRENCY_UPDATES_ENABLED. Полный go test ./... и локальная Docker-сборка прошли. На изолированной PostgreSQL проверены миграция старой строки, повторная миграция после EUR, неизменность цен и количеств, запрет PATCH при выключенном флаге, роли owner/manager, чужая организация, неверный код и CORS.

Web. Повторно прошли lint, TypeScript, production-сборка и локальная Docker-сборка. Через реальный Go API и изолированную PostgreSQL в браузере проверены вход, каталог и поиск, RSD → EUR → USD, подтверждение без конвертации, немедленное обновление профиля и dashboard, переводы RU/RS. Исправлены блокировка кнопки сохранения для пользователя без id в ответе login и гонка старого ответа при смене валюты.

iOS. Проверены подписанные Simulator-тесты, включая валютные и Keychain, сборка приложения и виджета. Подписанный архив 1.0 (60) загружен Xcode в App Store Connect. Пользователь установил TestFlight-сборку на используемый iPhone; devicectl независимо показал Bundle Version 60. После включения production PATCH пользователь повторил смену валюты на iPhone и подтвердил успешный результат. Отдельной независимой проверки изображения виджета на устройстве нет.

Репозитории и production. Backend PR #16, frontend PR #17 и iOS PR #12 слиты в main; обе сборки GitHub Actions завершились успешно. Перед обновлением создан Neon backup /root/jerkyvault/backups/jerkyvault-pre-currency-20260926T193400Z.dump, его каталог проверен через pg_restore --list; прежние образы помечены pre-currency-20260926, серверный Compose сохранён отдельно. Backend и web контейнеры обновлены. Переменная WORKSPACE_CURRENCY_UPDATES_ENABLED=true включена в production Compose после установки iOS 60. Первый запрос со старым выключенным флагом ответил 404 и на iPhone показал unknown error; после включения повторные PATCH отвечают 200.

Реальный путь и уборка. Изолированная production-организация прошла API RSD → EUR → RSD, неверный код дал 400. Второй временный аккаунт через опубликованный web-профиль выбрал EUR; dashboard показал 0 EUR во всех денежных карточках. Затем её валюта возвращена в RSD через API, подтверждена GET и тестовые membership/workspace/user удалены транзакцией (три строки). Финальная проверка: тестовых QA-пользователей 0, workspace с NULL 0, backend и frontend running без рестартов. В production теперь 8 workspace с RSD и один с AZN — пользовательский выбор, его не изменяли. Числовые значения PATCH не пересчитывает; это проверено отдельным PostgreSQL-тестом, а не снимком денежных данных реальной организации.

Откат после выпуска. Поскольку в рабочей организации уже выбрана валюта, отличная от RSD, старые образы с жёстким RSD нельзя возвращать. При проблеме сначала выключить WORKSPACE_CURRENCY_UPDATES_ENABLED, сохраняя валютно-совместимые чтение и отображение; не изменять выбранную валюту и денежные значения.
