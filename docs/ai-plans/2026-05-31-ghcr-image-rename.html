BatchVault GHCR Image Rename Plan

Created: 2026-05-31

Scope: Rename production GHCR images for the BatchVault frontend and backend, and update deploy references to match.

Task Summary

The GitHub repositories were renamed to BatchVault_Front and BatchVault_Back, but their GitHub Actions workflows still publish Docker images under the old package names: ghcr.io/dzarlax/jerky-vault-frontend and ghcr.io/dzarlax/jerky-vault-back. This plan changes the canonical image names to BatchVault names and updates the live deploy compose file to pull them.

Current Behavior

Component Current image Source of truth
Frontend workflow ghcr.io/dzarlax/jerky-vault-frontend:latest D:\Projects\Code\Personal\BatchVault\BatchVault_Front\.github\workflows\main.yml
Backend workflow ghcr.io/dzarlax/jerky-vault-back:latest D:\Projects\Code\Personal\BatchVault\BatchVault_Back\.github\workflows\main.yml
Live deploy compose Pulls the same old image names D:\Projects\Code\Personal\personal_ai_stack\deploy\jerkyvault\docker-compose.yaml

Desired Behavior

After merge, pushes to main publish:

  • ghcr.io/dzarlax/batchvault-front:latest and ghcr.io/dzarlax/batchvault-front:${{ github.sha }}
  • ghcr.io/dzarlax/batchvault-back:latest and ghcr.io/dzarlax/batchvault-back:${{ github.sha }}

The live deploy compose should pull the new batchvault-front and batchvault-back images.

Assumptions

  • The target package names batchvault-front and batchvault-back are acceptable canonical GHCR names.
  • The repository owner remains dzarlax.
  • Deploy keeps the existing hostnames admin.jerky.in.rs and api.jerky.in.rs.
  • This pass does not rename Docker compose service names or Traefik router labels.
  • This pass does not deploy to the VPS unless explicitly approved after images exist.

Implementation Steps

  1. Change frontend workflow tags from jerky-vault-frontend to batchvault-front.
  2. Change backend workflow tags from jerky-vault-back to batchvault-back.
  3. Update production deploy compose image references to the new names.
  4. Update non-historical docs and examples that users copy for deploys.
  5. Leave historical docs/ai-plans references alone unless they are part of this new plan.
  6. Run targeted grep checks to ensure active deploy/workflow files do not reference the old image names.

Test Plan

  • Run rg -n "jerky-vault-frontend|jerky-vault-back" .github DOCKER.md docker-compose.yml.example README.md in the frontend/backend repos as applicable.
  • Run docker compose -f D:\Projects\Code\Personal\personal_ai_stack\deploy\jerkyvault\docker-compose.yaml config --services.
  • After merge to main, verify GHCR packages with docker manifest inspect ghcr.io/dzarlax/batchvault-front:latest and docker manifest inspect ghcr.io/dzarlax/batchvault-back:latest.

Manual QA Checklist

  • Confirm GitHub Actions succeeded in both repositories after merge.
  • Confirm new GHCR packages are visible under the dzarlax account.
  • Before production deployment, confirm the VPS can pull both new private/public packages if visibility or permissions differ.
  • After production deployment, verify https://admin.jerky.in.rs/ and https://api.jerky.in.rs/swagger/index.html.

Risks

  • If deploy compose is updated before the new packages are published, the next deploy pull can fail.
  • If GHCR package visibility differs from old packages, the VPS pull may require authentication changes.
  • Old rollback docs and operators may still reference old image names.

Rollback Plan

  • Restore workflow tags to ghcr.io/dzarlax/jerky-vault-frontend and ghcr.io/dzarlax/jerky-vault-back.
  • Restore deploy compose image references to old names.
  • Redeploy from the old :latest images or pin a known-good old SHA tag.

Open Questions

  • Should local image examples use batchvault-front:local and batchvault-back:local too, or only remote GHCR images?
  • Should old GHCR packages remain untouched for rollback history?

  • Historical implementation plans may still mention old image and repository names as part of their original context.
