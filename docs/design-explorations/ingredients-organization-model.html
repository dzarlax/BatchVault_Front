Если продукт вырастет: рабочее пространство вместо “моих ингредиентов”

Чтобы не запереться в персональной модели, рабочий набор ингредиентов лучше проектировать как принадлежность workspace/company, а не напрямую user.

Целевая модель

Пользователь работает в контексте workspace. Ингредиенты в справочнике общие для инсталляции, но рабочий набор и цены принадлежат workspace.

usersЛюди, которые входят в систему.
workspaces / companiesМясная мастерская, кондитерка, тестовая кухня, команда.
users join workspaces via roles
workspace_membersuser_id + workspace_id + role. Здесь решаются доступы, а не в ingredients.
workspace owns working set
workspace_ingredientsworkspace_id + ingredient_id + active/archived + optional local name/category.
working set references shared dictionary
ingredientsОбщий installation-wide справочник для дедупликации и переиспользования.
prices are scoped to workspace
ingredient_pricesworkspace_id + ingredient_id + price + quantity + unit + date. История сохраняется.

Практичный путь

Не обязательно сразу строить весь SaaS-слой, но имена и связи лучше выбрать так, чтобы не переезжать через месяц.

Recommendation
1
Не называем `user_ingredients`Лучше `workspace_ingredients` или `ingredient_memberships`. Даже если сейчас workspace = personal workspace пользователя.
2
Создаем personal workspace автоматическиДля текущего продукта каждый user получает workspace по умолчанию. UI почти не усложняется.
3
Цены привязываем к workspaceИначе команда из двух людей не сможет иметь общий прайс-лист без дублирования.
4
Справочник остается общимЭто предотвращает дубликаты между командами, но не засоряет рабочий список каждой команды.
5
ЭтапностьПлан можно разбить: сначала schema/workspace default, потом ingredient screen, потом team UI/roles отдельно.
