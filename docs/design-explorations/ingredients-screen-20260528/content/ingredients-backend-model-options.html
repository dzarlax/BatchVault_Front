Backend развилка для “моих ингредиентов”

Чтобы не уйти в лишнюю сущность слишком рано, есть три рабочих варианта. Рекомендую B как явную, но контролируемую модель.

A. Выводить “мой набор” из фактов

Не добавляем новую таблицу. Пользовательский набор = ингредиенты, у которых есть цены, рецепты или сессии пользователя.

ingredientsОбщий справочник инсталляции
+
prices / recipesПо ним вычисляем, что пользователь использует
+Минимум backend-схемы.
-Нельзя добавить ингредиент в набор до первой цены/рецепта.
-Сложно архивировать и скрывать неактуальное.
Recommended

B. Явный рабочий набор

Добавляем связку пользователя и справочного ингредиента. Это не новый ингредиент, а membership.

ingredientsОбщий справочник инсталляции
↕
user_ingredientsuser_id + ingredient_id + active/archived + optional alias
↕
pricesИстория цен пользователя для ingredient_id
+Чистый default view без чужих доменов.
+Можно добавить в набор до первой цены.
-Нужна миграция и новые endpoint’ы.

C. Workspace/domain layer

Заводим сущность бизнеса/пространства: мясное производство, кондитерка, тестовый workspace.

workspacesBusiness/domain boundary внутри инсталляции
↕
workspace_ingredientsНабор ингредиентов конкретного workspace
↕
pricesЦены workspace или пользователя в workspace
+Самая правильная multi-tenant модель на будущее.
-Сильно расширяет продукт: роли, доступы, миграции.
-Слишком большой шаг для одного экрана.
